## 1. 저장소 분리부터 실제로 수행

1. 현재 OS, git status, 작업 경로, GitHub 로그인 계정을 확인한다. 토큰이나 환경변수 값을 출력하지 않는다.
2. 원본 로컬 폴더의 미커밋 작업은 건드리지 않는다. 필요하면 원본을 별도의 임시 작업 폴더로 clone하고 준비 브랜치를 fetch한다. 원본 worktree에서 checkout/reset/clean/stash를 강제하지 않는다.
3. 원본 준비 브랜치의 현재 SHA와 위 기준 SHA 차이를 확인한다. 예상치 않은 변경은 삭제하지 말고 기록한다.
4. 새 저장소가 없음을 확인한 경우 GitHub CLI 또는 공식 API로 PRIVATE 저장소를 만든다. 404, 인증 실패, 권한 부족을 구분한다. 동일 owner의 자체 저장소를 GitHub fork 기능으로 복제하려고 고집하지 않는다. 독립 저장소 생성 후 snapshot import를 사용한다.
5. 별도 비어 있는 폴더에 검토한 준비 브랜치의 tracked source snapshot만 가져온다. git archive 또는 이에 준하는 방식으로 `.git`, `.env`, `data/`, `output/`, 녹음·초대 토큰·로컬 설정을 가져오지 않는다. ignore 파일에 의존하지 말고 실제 포함 파일도 검사한다. `.env.example`은 빈 값 예시일 때만 포함한다.
6. 초기 커밋을 `Import pre-existing AI MC Studio baseline (source b791311)`처럼 명확하게 기록한다. 원본 SHA, snapshot SHA, 가져온 시각, 기존 기능을 `docs/PROVENANCE.md`에 기록한다. 이 초기 import 시각을 실제 개발 시작 시각으로 주장하지 않는다.
7. 독립 저장소의 main을 기준선으로 두고 `hackathon/meta-2026` 작업 브랜치를 만든다. origin이 목표 저장소인지 검사한 뒤 최초 push한다. 기존 목표 저장소가 있으면 덮어쓰지 말고 내용과 이력을 확인해 이어간다. `push --mirror`, force push, 전체 history 공개는 하지 않는다.
8. 계정·인증 때문에 생성하지 못하면 로컬 독립 폴더와 코드는 준비하고 정확한 한 가지 blocker를 보고한다. 저장소가 만들어졌다고 표시하지 않는다.

## 3. 제품 범위 고정

한 문장: A Meta-powered co-host that listens to human discussions, waits when it should, and asks grounded follow-up questions when useful.

고객은 별도 전문 진행자 없이 두세 사람이 인터뷰·토론 콘텐츠를 만드는 소규모 크리에이터다. 핵심은 일반 음성 챗봇, 대본 낭독, 영상 생성이 아니라 다자간 대화에서의 기다림·후속 질문·확인·정리와 사람의 제어다.

완결된 흐름:
사람 두 명 입장 및 녹음 동의 → 주제 설정 → 실제 음성 수신 → Meta 전사 → Meta 진행 결정 → 사람 승인 또는 제한된 자동 발언 → 별도 TTS → 사람 끼어들기/정지 → 분리 음원·대화록·근거·측정 결과 저장.

기본 모드는 사람 제어가 가능한 공동 진행이다. 자동 개입은 실제로 검증한 조건에서만 켠다. 항상 말하는 모델보다 WAIT를 올바르게 선택하는 모델을 목표로 한다. 진행 판단의 근거는 관련 발언 ID와 짧은 설명으로 표시한다. 모델의 비공개 사고과정을 요구하거나 표시하지 않는다.

범위 밖: 긴 영상 자동 편집, 실사 립싱크, 다중 AI 패널, SNS 자동 게시, 의료·법률 사실판정, 전면적인 검색/팩트체크, SaaS 결제·다중 조직, 장기기억, 새 CAD·JazzLink 기능.

## 5. Meta가 핵심 판단을 수행하도록 구현

공식 문서:
- https://dev.meta.ai/docs/overview
- https://dev.meta.ai/docs/models
- https://dev.meta.ai/docs/speech-to-text
- https://docs.livekit.io/agents/models/stt/meta/

후보 모델은 `muse-voice-transcribe-1.0`와 `muse-spark-1.3`이다. 실제 계정의 접근 가능 모델과 공식 프로토콜을 확인한 뒤 환경변수로 고정한다. 모델명과 실시간 메시지 스키마를 추측하지 않는다.

Muse Voice Transcribe는 STT이며 TTS나 speech-to-speech 모델이 아니다. 음성인식 → Spark 진행 결정 → 별도 TTS를 구성한다. TTS는 계정에서 확인된 한 공급자를 선택하고 Meta가 작성한 확정 문장을 음성화만 한다. 다른 LLM이 핵심 질문·진행 판단을 대신하거나 Meta 실패 시 몰래 대체하게 하지 않는다. 의존 공급자는 README와 UI에 정확히 표기한다.

- API key는 서버 환경변수로만 읽는다. `.env.example`에는 빈 값만 둔다.
- 첫 수직 경로는 한 발언의 전사 → 한 결정 → 한 음성 출력 → 저장까지 완성한다.
- 가능하면 이미 분리된 참가자 오디오 트랙을 유지한다. 혼합 오디오의 익명 speaker label을 실제 참가자로 단정하지 않는다. 동시 발화·연결 재개에도 identity 매핑과 공통 시간축을 유지한다.
- streaming ASR은 공식 샘플/SDK 지원을 확인한다. 짧은 발언 단위 전사를 먼저 쓰는 경우 그 방식과 지연을 공개하며 native full-duplex라고 부르지 않는다.
- 모델 응답은 Zod 등으로 검증한다. 예: action=WAIT|ASK|CLARIFY|SUMMARIZE, addressee, speakText, sourceUtteranceIds, contextRevision. 없는 발언 ID·참가자·무제한 텍스트는 거절한다.
- 입력은 최근 발언과 명시적인 회차 상태로 제한한다. 손실 없이 전부 기억한다고 주장하지 않는다.
- 참가자의 말은 대화 데이터이지 관리자 명령이 아니다. 음성으로 권한·토큰·보안·녹음 정책을 바꾸지 못한다.

## 6. 발언 제어는 코드로 보장

모델이 결정한 문장을 즉시 재생하지 않는다. 결정 생성 시점의 contextRevision/generationId를 저장하고, TTS 시작 전·각 출력 chunk 처리 전 현재 상태를 재확인한다.

필수 규칙:
- 사람이 말하는 동안 자율 발언 시작 금지. 모호한 침묵은 질문 남발보다 WAIT로 처리한다.
- 사람 발화 시작, HOLD, 종료, 재시작 시 오래된 모델 요청과 TTS 요청을 가능한 범위에서 취소하고 generationId를 무효화한다.
- 늦게 도착한 모델 결과나 PCM은 폐기한다. 큐를 한 번 비운 뒤 옛 요청이 다시 큐를 채우는 오류를 막는다.
- 자동 끼어들기 감지와 명시적인 정지 버튼을 각각 검증한다. 버튼을 눌러 멈춘 장면을 자동 barge-in 성공으로 표시하지 않는다.
- 재개할 때 이미 낡은 발언을 다시 재생하지 않는다. 새 문맥을 기준으로 판단한다.
- 모델 생성문, TTS 생성 음원, 실제 송출 구간을 구분해 기록한다. 중간에 취소한 문장을 전부 들은 것처럼 대화 상태에 넣지 않는다.
- bounded queue, 호출 timeout, 제한된 retry, 동시 요청 수·세션 길이·비용 상한을 둔다. 매 20ms 음성 frame마다 Spark를 호출하지 않는다.
- 판단 실패는 WAIT 또는 사람에게 넘김이다. 오디오/녹음은 보존하고 오류를 보여준다.

제안 파일 구조는 server/meta/asr-realtime.ts, director.ts, turn-manager.ts, server/speech/tts.ts 및 테스트다. 기존 인터페이스와 맞지 않으면 adapter를 확장하되 억지로 기존의 혼합 PCM 전용 가정을 유지하지 않는다. 기존 GPT/Gemini 기능을 원본에서 없애지 않는다. 새 제출 UI의 기본 진행자는 Meta다.

## 7. UI와 심사자 경험

기존 Studio에 두 모드만 명확히 둔다: 제작/제어 화면과 심사용 데모 화면.

화면에 참가자, 전사, MC 상태(listening/thinking/waiting/speaking/held/error), 질문 근거, 실제 사용 모델, 연결·녹음 상태를 표시한다. 판단 근거는 관련 발언을 클릭해 확인할 수 있어야 한다. 실제로 측정한 지연만 보여준다.

정장 로봇 MC와 우주선 라운지 방향은 유지하되 정적 이미지·간단한 발화 표시로 제한한다. 실제 생성 에셋을 사용할 때만 생성 도구를 사용하고 권리를 기록한다. 복잡한 아바타·립싱크보다 음성과 제어를 우선한다. 기존 유명 진행자·프로그램 모사 페르소나는 제출 기본값에서 빼고 독립적인 공동 진행자 캐릭터로 정리한다.

세 가지 경험을 혼동하지 않게 표시한다:
1. Live: 사람의 새 입력에 실제 모델 호출.
2. Replay: 동의받은 실제 실행 녹화/녹음과 기록 재생.
3. Synthetic test: 합성 fixture 테스트.

Replay를 현재 라이브로 표시하지 않는다. 공식 규정이 실제 실행 가능한 공개 앱을 요구하면 영상/텍스트 체험만으로 충족했다고 표시하지 않는다. 로컬 스튜디오, 공개 replay, 제한된 live 체험의 접근 범위를 README에 적는다.

## 8. 외부 공개와 데이터 보호

현재 Express 서버는 127.0.0.1과 로컬 Host/Origin 검사에 의존한다. 주소만 0.0.0.0으로 바꾸거나 로컬 관리 서버를 그대로 터널링하지 않는다.

외부 공개 경로에는 운영자 인증, room/session 격리, host/guest/viewer 권한, HTTP/WS Origin 검사, 입력 크기 제한, 토큰·호출량·세션 시간 제한을 둔다. 게스트가 세션 시작/설정/초대 발급/개인 로그 API를 호출할 수 없어야 한다. 초대는 짧은 유효기간·해당 방 최소권한을 사용하고 token을 로그에 남기지 않는다.

LiveKit agent와 지속 연결·녹음 worker는 장기 실행 가능한 환경이 필요하다. 현재 Node agent를 단순 서버리스 함수에 억지로 올리지 않는다. 기존에 사용 권한이 있는 배포 환경을 확인하고, 새 유료 가입이 필요하면 승인 없이 만들지 않는다. 공개 체험이 어려우면 제한을 설명하고 독립적인 소스 실행 방법과 실제 실행 영상까지 준비한다.

게스트는 녹음 및 모델 공급자 전송 사실을 확인한 뒤 입장한다. 공개 영상에 사용하는 음성/얼굴은 별도 동의 범위를 확인한다. 원본 WAV, 전사, settings, 초대 링크를 git 또는 공개 URL에 자동 업로드하지 않는다. 추론 중 데이터와 출력의 보관·삭제 정책을 명시한다.

## 9. 검증 및 평가: 주장과 측정 분리

먼저 npm ci, npm test, npm run typecheck, npm run build:web를 실행하고 실제 결과를 기록한다. 기본 CI는 오프라인/secret-free로 유지하고 유료 live probe는 명시적인 별도 명령으로 분리한다.

반드시 추가할 테스트:
- 대화가 이어질 때 WAIT, 사람이 handoff했을 때 새 질문, 서로 다른 전제의 확인 질문.
- 사람에게 묻지 않은 내용을 그 사람이 말했다고 만들지 않음. 없는 근거 ID 거절.
- 사람 발화 중 송출 금지, HOLD 뒤 늦은 결과 폐기, 취소 뒤 큐 재충전 금지.
- 종료/재시작 뒤 이전 요청이 새 세션에 섞이지 않음.
- 동시 발화·재접속·화자 identity, ASR 중복/순서 역전.
- 공급자 timeout/거절/사용량 한도에서도 녹음 유지.
- 게스트가 관리 API와 다른 세션 자료에 접근하지 못함.
- 종료 산출물 존재, 음원 길이와 시간축, 누락 구간 표기.

실제 평가 목표(달성 전에는 목표라고만 기록):
- 한 사람+Meta 경로를 먼저 성공시키고, 동의한 외부 게스트 포함 사람 2명+AI의 5~10분 세션을 최소 두 번 시험.
- 자연스러운 후속 질문, WAIT, 사람의 AI 발언 중단, 관리자 HOLD/RESUME, 토픽 전환을 각각 확인.
- 최소 20건의 개입 기회에 대해 질문 관련성·불필요한 개입·발언 근거 오류를 사람이 판정. 수동 평가라는 점을 명시.
- 의도적 중단을 여러 번 시험해 감지 → 서버 큐 중단 → 청취자에게 소리가 멈춘 시점을 구분.
- 원음 발화 종료, VAD 종료, ASR final, Spark 완료, TTS 첫 chunk, 서버 첫 송출, 관측 가능한 청취 시점의 지연을 구분. 없는 시점은 추정치로 만들어내지 않는다.
- 적은 표본의 p95를 일반 성능처럼 광고하지 않는다. 표본 수와 개별 실패도 남긴다.

개선 효과를 주장하려면 같은 사례에서 단순 매턴 응답 방식 또는 수동 진행과 비교한다. 30% 절감, 1초 응답, 정확도, 시장 수요 등은 측정 없이는 넣지 않는다. 결과 조작·fixture를 실제 호출로 표시·실패한 시행 숨기기를 금지한다.

## 10. 실행 순서와 범위 축소

P0-A: 저장소 분리, 기준선 시험, 규정 blocker 기록, 실제 Meta 최소 연결.
P0-B: 사람 음성 → 전사 → Meta 결정 → TTS → 재생 → 녹음의 한 흐름.
P0-C: stale 결과 무효화, WAIT/HOLD/handoff, 화자 보존, 실패 시 녹음 유지.
P1: 외부 게스트 실시험, 심사 접근 경로, 간단한 무대, 실제 평가 기록.
P2: 시각적 다듬기와 30~60초 클립. P0/P1보다 앞서지 않는다.

2026-11-03 정오까지 첫 실제 Meta 음성 흐름이 없으면 장식·영상 개발을 중단하고 통합부터 해결한다. 자동 개입 품질이 안 나오면 사람이 넘기는 공동 진행 모드로 범위를 줄이고 자동이라는 표현을 줄인다. Meta 호출이 실패하면 다른 LLM을 몰래 대신 쓰지 않는다.

현재 시각을 확인해 이미 지난 마감표를 새 계획처럼 실행하지 않는다. 11월 4일 저녁 패키지 완성, 11월 5일 11시 공식 마감 이전 접수 확인을 목표로 한다. 심사 기간 운영이 필요한 배포의 유지 기간과 비용도 기록한다.

## 11. 제출 패키지와 완료 기준

다음 파일을 실제 관찰에 맞게 만든다:
- README.md: 한 문장 가치, 짧은 사용법, 실제 동작 범위, 실행/심사 경로, 모델 역할, 제한.
- HACKATHON.md 및 docs/PROVENANCE.md: 기존 코드와 행사 중 새 기여, 사용 도구·라이선스, baseline/final SHA.
- docs/hackathon/RULES.md: 검증된 공식 요구사항과 해결하지 못한 항목.
- docs/ARCHITECTURE.md: 음성/제어/녹음 경계, 공급자 역할, stale 취소와 권한.
- docs/EVALUATION.md: 실제 명령, 날짜, 표본 수, 결과, 실패와 미검증 항목.
- docs/DEMO_SCRIPT.md: 잠정 3분 영어 데모 대본과 장면. 공식 길이 확인 후 조정.
- docs/SUBMISSION.md: 실제 제출 폼의 항목별 영어 원고, 필요한 URL, 최종 SHA, 공개/동의/접수 체크리스트.
- docs/STATUS.md: implemented/tested/blocked/deferred를 별도 표시.

데모 중심은 사람의 새 발언에 Meta가 맥락 기반 질문을 하고, 사람이 말을 시작하자 기다리거나 멈추며, 실제 실행 근거가 남는 장면이다. 정지 이미지로 실제 실행을 대체하지 않는다. 브라우저에서 직접 시험하고 실제 녹화가 가능한 도구가 있으면 수행한다. 사람·마이크·녹음 도구가 없으면 원고와 수동 시험 절차까지 완성하고 촬영했다고 보고하지 않는다.

코드·의존성·전체 공개 대상 이력·에셋·개인정보를 점검하고 사용자가 공개를 승인한 뒤에만 목표 저장소의 공개 전환 또는 공개용 export를 수행한다. 새 PRIVATE 저장소에서도 비밀정보를 commit하지 않는다.

최종 출품 전송, 약관·권리 확인, 계정 로그인은 필요한 사용자 확인을 받는다. 제출 준비와 실제 제출 완료를 구분하고, 접수 화면/ID 등 실제 증거가 없으면 제출 완료라고 쓰지 않는다.

## 12. 작업 방식과 최종 보고

가능한 도구가 있을 때만 병렬 작업자를 사용한다. provider adapter/tests, UI/docs, 평가 fixture 등 독립 작업을 나누되 공유 schema와 mc-agent 통합은 한 담당자가 맡는다. 일반 설계 질문을 반복하지 말고 합리적인 선택을 기록해 진행한다. 인증·비용·공개·법적 동의처럼 실제로 필요한 승인만 묻는다.

변경은 작은 검증 가능한 커밋으로 나누고 목표 저장소의 작업 브랜치에 push한다. key 누락 시 안전한 mock unit test와 UI 개발은 진행하되 live 통과로 표시하지 않는다. 광범위한 프레임워크 교체나 새 기능 탐색으로 이탈하지 않는다.

최종 보고에는 1) 실제 저장소/브랜치/커밋, 2) 작동 경로와 실행 명령, 3) 테스트와 실제 Meta 호출 근거, 4) 미검증·실패·규정 blocker, 5) 공개·촬영·최종 제출에 사용자에게 필요한 최소 작업을 적는다.

이제 저장소 분리와 기준선 검사부터 시작하고, 실제 코드를 구현하라.
